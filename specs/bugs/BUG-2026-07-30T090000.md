# BUG-2026-07-30T090000: Stale VERSION file & Hardcoded test assertion

## Symptom

`git describe --tags` on `main` is at `v0.1.1`, but the `VERSION` file (and therefore the live footer at https://node.bigbase.click) still reads `0.1.0`. `server.test.js` passes falsely because it asserts `assert.ok(body.includes("0.1.0"))` instead of testing against the `VERSION` file dynamically.

## Root Cause Analysis (4-Phase)

1. **Reproduce**: `git describe --tags --abbrev=0` returns `v0.1.1`, but `cat VERSION` yields `0.1.0`. `server.test.js` hardcodes `"0.1.0"` so tests pass despite the stale `VERSION` file.
2. **Isolate**:
   - `server.js` reads `fs.readFileSync(path.join(__dirname, 'VERSION'), 'utf8')`.
   - `.github/workflows/test-build-release.yml` runs `big-release`, which creates a new git tag (e.g. `v0.1.1`) and updates `CHANGELOG.md`, but does not update `VERSION`.
   - `server.test.js` hardcodes string `"0.1.0"`.
3. **Hypothesis**:
   - `server.test.js` should dynamically read the `VERSION` file for its test assertions so that if `VERSION` is not served correctly or changed, the test enforces exact parity.
   - `.github/workflows/test-build-release.yml` should include a post-release step after `big-release` to retrieve the latest tag (`git describe --tags --abbrev=0`), strip the `v` prefix, update `VERSION`, and commit+push it back to `main` with `[skip ci]`.
4. **Verify**:
   - Dynamic `server.test.js` assertion: `const expectedVersion = fs.readFileSync(path.join(__dirname, 'VERSION'), 'utf8').trim();`
   - Test step in workflow updates `VERSION` post-release.

## Fix Plan

1. Update `server.test.js` to read `VERSION` file dynamically rather than hardcoding `"0.1.0"`.
2. Add post-release `Update VERSION file` step to `.github/workflows/test-build-release.yml` after `Run big-release`.
